## Lessons Learned

- **An absence claim ("X does not exist / is not present") must state both the scope searched and
  the exact command run — narrowing either without saying so silently overclaims.** This applies
  everywhere multi-location resources exist (global vs. project-local skill dirs, `find` depth
  limits, filtered search fields whose semantics don't match the question being asked). The fix
  isn't "be more careful" — it's structural: before writing `[verified]` on a negative claim, name
  the exact scope out loud in the same sentence, because that forces the check that the scope
  actually matches the claim.

- **A database/search field's name is not proof of what it semantically tracks — read one hit
  before trusting a filter.** `project:` in this Arra instance tracks the banking oracle, not the
  subject of the document. Any filter field with an intuitive-sounding name deserves one manual
  spot-check of an actual result before being used as evidence, especially in cross-oracle/
  cross-project knowledge systems where "who wrote this" and "who it's about" commonly diverge.

- **Distinctive-token exact-match search outperforms broad semantic/filtered search for a yes/no
  presence question.** A long natural-language query against a hybrid search system will silently
  route to vector-similarity (top-N ranking) even when full-text search is healthy, because
  nothing in the long query is FTS-exact. For a binary "does X exist in the corpus" question, a
  single unique term the corpus itself would only contain if the fact were true is a stronger
  probe than a well-worded paragraph.

- **A tool's own documentation claiming automatic behavior ("no separate call needed") is itself
  an operational claim requiring verification before other operational claims get built on top of
  it.** This generalizes past this specific skill: any "and it just handles X for you" line in a
  skill/tool doc should get one real probe before an oracle relies on it silently for weeks.
