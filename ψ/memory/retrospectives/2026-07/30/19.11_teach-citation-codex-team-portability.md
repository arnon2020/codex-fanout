## Honest Feedback

**Friction 1 — shell quoting broke a dispatch mid-session.** Sending a `maw hey` message containing inline-code backtick spans (`` `git worktree repair <new-path>` ``) caused a real bash syntax error locally (command substitution tried to execute the backtick content, and `<new-path>` inside it looked like invalid redirection). The message still landed at Citation intact — the error was noise from maw's own CLI startup output getting mixed into my terminal — but I spent a non-trivial chunk of turns confirming that before trusting it. Backtick-containing messages to `maw hey` need either escaping discipline or a habit of avoiding inline code spans in dispatch text.

**Friction 2 — inbox mark-read didn't work through the documented CLI path.** `maw inbox show --unread --mark-read` and `maw inbox read <filename>` both failed silently or errored (`could not mark read`) on 4 stale messages from a prior session. Root cause turned out to be that those 4 files lacked `read:` YAML frontmatter entirely (they'd been hand-written without it), so the mark-read logic — which mutates frontmatter — had nothing to mutate. Had to add the frontmatter manually via Edit before the standard flow worked. This is worth fixing upstream (either the inbox writer should always stamp `read: false` on creation, or the CLI should handle frontmatter-less files gracefully) rather than re-discovering per session.

**Friction 3 — cross-oracle dispatch context is one-way and lossy.** Every correction and every new finding I wanted Citation to act on had to be re-explained in full inside a `maw hey` message, because Citation's session has no visibility into my reasoning — only what I choose to write. This is by design (federation, not shared context) but it means the same explanation gets written twice: once as my own understanding, once as a teachable dispatch. When I skipped the second, careful version (the portability shortcut), the gap was invisible until the user checked Citation's memory directly — I had no way to verify from my side whether Citation's understanding was real or transcribed without going and reading their files myself.

## Lessons Learned

- **A fix I verify with a static check (grep, diff review) is not the same claim as "the recipient understands it" — those require different evidence, and conflating them is a specific, repeatable failure mode.** When teaching another agent, don't just apply and hand over a fix, even when the fix is correct and even when time pressure or "this wasn't something they could have known" makes it feel unnecessary to make them re-derive it. Give a task with a required proof step every time, or the taught party's memory silently degrades into transcription.
- **"Must survive relocation" or similar infra requirements have layers — check the running system, not just the document that describes how to build it.** A skill file with correct placeholders can still describe infrastructure (git worktrees, registry caches, tmux sessions) that has its own independent, undocumented absolute-path assumptions. Test the actual mechanism, not just the instructions for the mechanism.
- **When a fix involves an external tool's semantics you're not 100% certain of (e.g. exactly how `git worktree repair` resolves paths, or whether it must run from a specific location), build a disposable reproduction and run it before writing the fix into anything durable.** Recall-based technical writing reads exactly as authoritative as tested writing, which is what makes it dangerous — the difference only shows up when someone runs it.
- **A recurring user correction pattern ("don't do X") is not satisfied once — it needs to be re-applied at every subsequent decision point, including ones that don't superficially resemble the original violation.** "Don't teach shallowly" was given once about Citation's understanding of maw mechanics; it silently also applied to my own portability fix two steps later, and I only caught it because the user asked a pointed follow-up rather than because I generalized the rule myself.
