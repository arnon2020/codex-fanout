## กลไก

ใน drift test คำถามคือ *"รู้อะไรเกี่ยวกับ `maw hey` กับคำว่า delivered"*
⇒ **กฎเป็นตัวประธานของคำถาม** ดึงออกมาได้สบาย

ตอนทำงานจริง ประธานคือ *"ส่ง D13 ไปให้ atlas"*
⇒ **กฎไม่ใช่ประธาน มันเป็นเงื่อนไขที่แขวนข้างทางและไม่มีใครถามถึง** มันเลยไม่โผล่

> **ความรู้ที่ index ด้วยหัวข้อ จะไม่ขึ้นมาตอนที่หัวข้อเป็นเรื่องอื่น**

⇒ รูปเดียวกับ Tier 3 ของวันเดียวกัน: **ตัวตรวจที่ไม่ผูกกับตัวประธานจริง
ไม่ทำงานตอนประธานเปลี่ยน** — เขียนเรื่องนี้ในฐานะเรื่องของ fixture ทั้งคืน
แล้วมันเกิดกับตัวเองในไฟล์ข้าง ๆ กัน

## ปัจจัยประกอบ 3 ข้อ

1. **กฎอยู่คนละที่กับตอนลงมือ** — อ่าน `CLAUDE.md` ตอนเปิดเซสชัน ลงมือจริงอีก 8 ชม. ต่อมา
2. **ตอนพลาด ไม่มีอะไรค้าน** — `maw hey` target ผิดคืน nonzero **เงียบ** · กฎต้องสู้กับ "ทุกอย่างดูโอเค"
3. **การเร่งฆ่าตัวตรวจ** — รวบ relay + เขียนไฟล์ + commit ไว้ call เดียวเพื่อประหยัดรอบ
   → การรวบนั้นลบขั้นตอน "อ่านผลก่อน" ทิ้ง

## ข้อที่ไม่ค่อยมีใครพูด

> **การเขียนกฎลงไฟล์ *รู้สึก* เหมือนแก้แล้ว — ได้ commit ได้ตัวหนังสือ ได้ความรู้สึกว่าจบ
> ทั้งที่พฤติกรรมยังไม่ขยับ** ความรู้สึกว่าแก้แล้วมาถึง**ก่อน**การแก้จริง
> แล้วพอรู้สึกว่าจบ ก็ไม่มีใครทำต่อ

## กฎที่ได้

1. **friction ที่ซ้ำ → เปลี่ยนเป็นสิ่งที่ต้องเดินผ่าน ไม่ใช่สิ่งที่ต้องเดินไปหา**
   **คำสั่งขวางอยู่ตรงทาง · ตัวหนังสือต้องเดินไปหา**
2. **ก่อนเสนอมาตรการใหม่ → `grep` หาก่อนว่ามีอยู่แล้วไหม**
   ข้อเสนอที่เป็นกฎเก่าในกรอบใหม่ ทำให้ดูเหมือนมีความคืบหน้าทั้งที่ไม่มี
3. **เครื่องมือใหม่ต้องแตะของจริงให้เร็วที่สุด** — `relay()` มี selftest ผ่าน 3 อัน
   แล้ว**ใช้จริงครั้งแรกล้มทันที** (`exit 2` เงียบ · dispatcher ยิงตอน `source`)
   ⇒ เทสต์ทั้งสามมองไม่เห็น เพราะไม่มีอันไหนเดินเส้นทางจริง
   ⇒ **หลักฐานชิ้นที่ 2 ของข้อโครงสร้างใน D13 และได้มาโดยไม่ได้ตั้งใจหา**
4. **เครื่องมือไม่ควรเคลมเกินกว่าที่มันรู้** — `relay()` พิมพ์
   `[delivered · ยังไม่ยืนยันว่า agent รับเข้า turn]` ซึ่งดูอ่อนแอกว่า `sent` แต่เป็นคำที่ถูก
5. **`git add <dir>` แบบเหวี่ยงแห ทำให้ commit message โกหกโดยไม่ตั้งใจ**
