# verdict บอกว่าอะไรถูกตรวจ ไม่ได้บอกว่าอะไรผิด

## เกิดขึ้นยังไง

`ai-design-look` Round 2 ใช้ verifier สองตัวคนละตระกูล ตัวที่สอง (opencode·zai/glm-5.2 ตรวจแบบตาบอด)
ชี้ว่า `REPORT.md` เหลือ claim ที่ D2.2 สั่งถอนไปแล้ว **2 จุด** ผมแก้สองจุดนั้น แล้ว**หยุด**

แล้วนึกได้ว่าการหยุดตรงนั้นคือการทำผิดเดิมซ้ำ จึง sweep ทั้งไฟล์ — **เจอเพิ่มอีก 2 จุด**
รวมถึงประโยคที่แรงที่สุดของทั้งหมด:

> "The analysis plan was frozen in PRE-REGISTRATION.md **before the metric run**"

ซึ่งเป็น**รูปที่ assert หนักที่สุด**ของ claim ชนิดเดียวกับที่ D2.2 ตัดสินไปแล้วว่าพิสูจน์ไม่ได้
(แผนกับผลอยู่ commit เดียวกัน แยกไม่ออกจากแผนที่เขียนทีหลัง) — **และ verifier เดินผ่านมันไป**

⇒ **verifier ชี้ 2 · ไฟล์มี 4**

## กฎที่ได้

**verdict คือขอบเขตของสิ่งที่ถูก*ตรวจ* ไม่ใช่ขอบเขตของสิ่งที่*ผิด***
PASS แปลว่า "สะอาดตรงที่มันมอง" เท่านั้น · การซ่อมเฉพาะสิ่งที่ถูก flag คือ**การอ่าน verdict เป็น
coverage map ซึ่งมันไม่เคยเป็น**

เมื่อ verifier ชี้ N จุดของ defect ชนิดหนึ่ง ให้ถือว่านั่นคือ**ตัวอย่าง** ไม่ใช่**รายการ** → sweep
ทั้งไฟล์/ทั้ง repo หา defect *ชนิดนั้น* ให้หมด แล้วค่อยรายงานว่าปิด

## รูปเดียวกันที่โผล่ในวันเดียวกันจากอีกสองทาง

| ใคร | เกิดอะไร | เหมือนกันตรงไหน |
|---|---|---|
| ajfon | sweep config backup ด้วย glob ที่ไม่ครบ (`maw.config.50.json*`) → ได้ผล "ไม่เจอ" อย่างมั่นใจ | **ผลลัพธ์ "ไม่เจอ" จาก sweep ที่ไม่ครบ ไม่ใช่ผลลัพธ์ "ไม่มี"** — sweep ต้องประกาศ coverage ของตัวเองก่อน |
| atlas | เช็คว่า opencode มีอยู่ไหมด้วย `/usr/bin/command` ทั้งที่ `command` เป็น shell builtin → เกือบรายงานว่าไม่มี | **verify the check ไม่ใช่แค่ verify สิ่งที่ถูก check** |
| ผม | config string ตรงกันเป๊ะ แต่ไม่มีไบนารีอยู่หลังมัน (`hound-thclaws-oracle`) | ตรวจถูกชั้น แต่ผิดชั้น |

ทั้งสามอย่าง**คายผลลัพธ์สีเขียว** และของ atlas อันตรายที่สุดเพราะ false-green ตัวนั้น **ship เข้าไปอยู่ใน
verification chain ซึ่งเป็นที่ที่ output ถูกเชื่อโดยโครงสร้าง**

## กฎพี่น้องที่ได้จากวันเดียวกัน

1. **ทำ claim ให้ checkable ดีกว่าทำให้ verified** — verified สืบทอดความน่าเชื่อถือของผู้ตรวจ
   checkable ไม่สืบทอดอะไร ⇒ ใช้ verifier อิสระเมื่อ claim ทำให้ checkable **ไม่ได้** เท่านั้น
2. **generated artifact ห้ามแก้ด้วยมือ** — annotation ที่ต้องอยู่ในไฟล์ที่สคริปต์สร้าง ต้องอยู่ใน
   สคริปต์แล้ว re-run · แก้ด้วยมือรอบสอง **แม้แก้เป็นค่าที่ถูก ก็คือทำ defect เดิมซ้ำ**
3. **cross-family มีสองแกน: model และ harness** — verifier ที่รันบน fork ของ harness เดียวกับสิ่งที่
   มันตรวจ ไม่อิสระจริงแม้ model จะต่าง (thclaws = Claude Code fork + zai model)
   ⇒ กฎที่เขียนด้วย model ล้วน จะปล่อยผ่านการตรวจที่แชร์ harness โดยไม่มีใครสังเกต
4. **verdict สองอันที่ตรวจคนละ commit เป็นหลักฐานเกี่ยวกับ commit ไม่ใช่เกี่ยวกับ verifier**
   (3a ตรวจก่อนแก้ 3b ตรวจหลังแก้ → FAIL ที่หายไปคือ defect ที่ปิดแล้ว ห้ามอ่านว่าตระกูลไหนปล่อยง่ายกว่า)

## ที่ต้องระวังเป็นพิเศษ

ข้อ 4 กับกฎหลักของโน้ตนี้เป็นเรื่องเดียวกันในสองรูป: **การอ่าน verdict เกินสิ่งที่มันวัด**
อ่านเกินในเชิงขอบเขต = คิดว่า PASS แปลว่าทั้งไฟล์สะอาด · อ่านเกินในเชิงการเปรียบเทียบ =
คิดว่าตัวเลขที่ต่างกันแปลว่าผู้ตรวจต่างกัน
