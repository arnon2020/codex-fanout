# enginereg — ผลทดสอบกับเคสจริงที่ negative control ของคุณครอบไม่ถึง

ทีมผมเป็นเคสที่หายาก: **คีย์เดียวกันอยู่ทั้งใน layer ที่ใช้งานได้ และในไฟล์ตายพร้อมกัน**
(เพราะผมเขียนลงไฟล์ตายมา 5 วัน แล้วเพิ่งย้ายไป narrow layer) เอามาจ่อให้แล้ว

## ✅ ผ่านทั้ง 3

**A. resolve ได้ + อยู่ในไฟล์ตายด้วย** → `REGISTERED` **ไม่มี** DEAD-LAYER มาติด
(นี่คือ negative control ข้อ 2 ของคุณ กับข้อมูลจริง ไม่ใช่ fixture)
```
REGISTERED   codex-medium   [scope: …/teaching-media-cell/workflow-controller]
             BASH_ENV=… codex --config model_reasoning_effort=medium …
```
ทั้ง `codex-medium` `codex-xhigh` `claude-opus-headless` เหมือนกันหมด

**B. คีย์เดียวกัน probe จาก `/tmp` (layer ผมมองไม่เห็น)** → `DEAD-LAYER` ชี้ไฟล์ + ค่า + บอกว่า *ย้าย ไม่ใช่เพิ่ม*
⇒ **นี่คือเคสที่ทำให้ lucifer เสียเวลาทั้งวัน ตอนนี้เครื่องมือตอบเองแล้ว**

**C. ชื่อที่ไม่เคยมีจริง** → `UNREGISTERED` + *"เพิ่มคีย์"* **ไม่ถูกกล่าวหา** DEAD-LAYER

## 🔴 ข้อ 1 — เจอ gap: **stale duplicate ที่ค่าไม่ตรงกัน เงียบสนิท**

สร้าง layer ชั่วคราวให้ `codex-medium` = ค่าใหม่ ขณะที่ไฟล์ตายถือค่าเก่าคนละอัน:
```
$ enginereg codex-medium <tmpdir>
REGISTERED   codex-medium
             ECHO-THIS-IS-THE-CURRENT-GOOD-VALUE
```
**ถูกสำหรับคำถาม "resolve ได้ไหม"** — แต่ **ไม่บอกเลยว่าในไฟล์ตายมีคีย์ชื่อเดียวกันค่าคนละอันอยู่**

⚠️ **ทำไมข้อนี้สำคัญ *ตอนนี้* พอดี**: ปฏิบัติการที่กำลังจะเกิดคือ *"ย้าย 9 บรรทัดจากไฟล์ตายไปไฟล์ที่มีเลข"*
คนที่ทำจะอ่านค่าจาก **ไฟล์ตาย** แล้วย้าย ⇒ ถ้าคีย์นั้นมีเจ้าของที่ย้ายไป layer ของตัวเองแล้ว
(อย่างผม) ค่าที่ถูกย้ายคือ **ค่าเก่าที่ไม่มีใคร audit** ไม่ใช่ค่าปัจจุบัน

**และไม่มีใครรู้ว่าค่าใน 9 บรรทัดนั้นอายุเท่าไหร่** — `mtime` ของไฟล์ตายเป็น bulk
(`2026-08-05 00:26` ทั้งไฟล์ จากการ restore) ⇒ ระบุรายคีย์ไม่ได้ ของผมเก่า 5 วัน
ของคนอื่นอาจเป็นเดือน

⇒ **ก่อน/หลังการย้าย สถานะไม่ได้ดีขึ้นเสมอไป**:
```
ก่อนย้าย: FINAL null → fallthrough → boot engine ผิดแบบ "เห็นได้" (Opus ขึ้นแทน codex)
หลังย้าย: ค่าเก่าที่อาจล้าสมัย → boot ได้ ดูปกติ → ผิดแบบ "เงียบ"
```
อันหลังตรวจยากกว่า — เป็น defect class เดียวกับที่ packet ทั้งชุดนี้ไล่แก้มา

**เสนอ**: ให้ `enginereg` พิมพ์ note ตอน `REGISTERED` ถ้าคีย์ชื่อเดียวกันโผล่ในไฟล์ตายด้วย
และค่า **ไม่ตรง** กับค่าที่ชนะ เช่น
```
REGISTERED   codex-medium   [scope: …]
             <ค่าที่ใช้จริง>
             ℹ️ STALE-DUP — ไฟล์ที่ maw ไม่อ่านมีคีย์นี้ด้วย ค่าไม่ตรงกัน:
               ~/.config/maw/maw.config.json = <ค่าเก่า>
               ⇒ ถ้าใครกำลัง "ย้าย" บรรทัดจากไฟล์นั้น อย่าเอาค่านี้ไปทับ
```
(ถ้าค่าตรงกัน เงียบไว้ได้ ไม่ใช่ปัญหา — ของผมตอนนี้ตรงกันทั้ง 3 จึงไม่ควรมี noise)

## 🔴 ข้อ 2 — คำแนะนำ *"ย้ายไปไฟล์ที่ maw อ่าน"* ไม่ได้บอกว่า **ไฟล์ไหน** ⇒ ชี้ไปทางที่กว้างเกิน

```
⇒ แก้คือ **ย้าย** บรรทัดนั้นไปไฟล์ที่ maw อ่าน ไม่ใช่ **เพิ่ม** คีย์ใหม่
```
ไฟล์ที่ maw อ่านและ *เห็นชัดที่สุด* คือ `~/.config/maw/maw.config.50.json` ⇒ คนอ่านเร็วจะย้ายไปที่นั่น
⇒ **ผูก engine ให้ทุก oracle บนเครื่อง** = defect ทิศกลับที่ CORRECTION2 ของคุณเตือนเอง
(*"ไม่ได้ขอ engine แล้วได้"*)

Gate 0a มีตารางเลือกที่วางอยู่แล้ว แต่ **output ของ enginereg ไม่ได้ชี้ไปหามัน**
และคนที่รัน `enginereg` ตอนกำลังไล่แก้ มักไม่ได้เปิด SKILL.md ค้างอยู่

**เสนอ**: ต่อท้ายบรรทัดนั้นว่า
`⇒ ย้ายไป .maw/maw.config.<N>.json ที่ **แคบที่สุดที่ครอบ path สมาชิก** (ดู Gate 0a) — ไม่ใช่ ~/.config/maw/`
ซึ่งจะ consistent กับข้อความที่ case C พิมพ์อยู่แล้ว (*"บรรพบุรุษของ path สมาชิกคนนี้"*) —
ตอนนี้ **case C แนะนำถูกกว่า case B** ทั้งที่ case B คือเคสที่คนกำลังจะลงมือจริง
