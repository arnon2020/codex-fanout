## กติกา 4 ข้อ ก่อนพิมพ์คำว่า "ตรวจแล้ว"

**1. ตัวตรวจแมตช์ตัวเองได้ไหม**
สตริงเป้าหมายอยู่ใน command line ของคำสั่งตรวจ ⇒ มันจะนับ/เจอตัวเองเสมอ

**2. ทิ้ง output ไปหรือเปล่า**
คำถาม "ของขึ้นไหม" ตอบด้วย output ไม่ใช่ด้วย exit code เพียงอย่างเดียว

**3. query ครบขอบเขตไหม**
sweep/glob/grep ที่ไม่ครบ ให้ผล "ไม่เจอ" ที่**ไม่ใช่** "ไม่มี" — ต้องประกาศ coverage ก่อน

**4. ตรวจถูกชั้นไหม**
string ตรง ≠ ไฟล์มี · ไฟล์มี ≠ รันได้ · รันได้ ≠ ทำงานถูก · จอบอก ≠ ปลายทางได้รับ

## ก่อนกด "รายงาน" — ถามตัวเอง 3 ข้อ

1. **ถ้าผลออกมาตรงข้าม ตัวตรวจนี้จะบอกผมได้ไหม** — ถ้าไม่ แปลว่ามันตอบไม่ได้ ไม่ใช่ว่าคำตอบคือ "ผ่าน"
2. **ผมกำลังตรวจงานของคนอื่นอยู่หรือเปล่า** — ถ้าใช่ ให้รันตัวตรวจซ้ำด้วยวิธีที่สองที่ไม่ใช้กลไกเดียวกัน
3. **เหตุผลที่ผมยกมาสนับสนุนเครื่องมือ ทำซ้ำได้จริงไหม** — 2026-08-04 atlas ทดสอบเหตุผลของผม
   แล้วพบว่ามันไม่ reproduce · เครื่องมือยังจำเป็น แต่เหตุผลผิด · **primitive ที่ป้องกันด้วยเหตุผล
   ที่ทำซ้ำไม่ได้ จะถูกคนถัดไปที่ทดสอบมันลบทิ้ง** · และอย่าอธิบายความพลาดเชิงวินัย
   ("ผมไม่ได้ตรวจเลย") ว่าเป็นข้อบกพร่องของเครื่องมือ — มันทำให้แก้ผิดที่
4. **สิ่งที่ผมกำลังจะพูด เป็นการตรวจ หรือเป็นการเดาที่ฟังดูดี** — รวมถึง**คำสารภาพผิด**
   (2026-08-03: ผมประกาศว่าทำข้อความของ arnon หาย ทั้งที่บัฟเฟอร์ว่างมาแต่แรก —
   **สารภาพผิดโดยไม่ตรวจ ก็เป็น claim ที่ไม่ได้ verify** และหลอกคนง่ายกว่า)

## วิธีใช้สคริปต์

```bash
S=ψ/teams/scripts/verify-check.sh
bash $S selftest                          # รันก่อนเชื่อมัน ทุกครั้งที่เครื่องเปลี่ยน
bash $S binexists thclaws                 # OK / MISSING / STALE / NOEXEC
bash $S procs codex                       # นับจาก /proc/*/exe — นับตัวเองไม่ได้
bash $S procs_cmd 'bin/codex'             # แมตช์ cmdline แต่ตัดตัวเอง+บรรพบุรุษออก
bash $S alive thclaws
bash $S bootprobe "$ENGINE_CMD" 8 thclaws # เก็บ output เสมอ + บอก VERDICT
```

`selftest` ปัจจุบัน: **8 ข้อ ผ่านครบ · stderr 0 บรรทัด** `[verified 2026-08-04]`

สองข้อในนั้นมีอยู่เพราะ **เครื่องมือนี้เองเคยโกหก**:
- ข้อ `6` — selftest เวอร์ชันแรก **ตกเอง**ด้วยกับดัก `pipefail` ที่มันควรจะดัก
- ข้อ `5b` — เพิ่มหลัง atlas พิสูจน์ว่าเหตุผลเดิมของ `binexists` ผิด · ตอนนี้มันทดสอบ
  **เคส hash-cache ที่ `command -v` โกหกจริง** แทนที่จะทดสอบเคส dangling ที่ `command -v` จับได้อยู่แล้ว

**สองการค้นพบอิสระที่ชนกันพอดี 2026-08-03→04**

| ใคร | เจอจากปลายไหน |

| **ajfon (D6)** | หลักการเดียวกันในสายการสื่อสาร: *"having raised an alarm creates an obligation to take it down"* ⇒ เขาถอน escalation ที่ส่ง tars ทันทีที่วัดใหม่แล้วพบว่าหาย |

> **infrastructure claim มีวันหมดอายุ · timestamp บอกว่ามันจริง _ตอนไหน_
> มีแต่การวัดซ้ำ ณ จุดใช้งาน ที่บอกว่ามัน _ยังจริงอยู่ไหม_**

### กลไก ไม่ใช่คติ: ปักด้วย **เงื่อนไขที่รันได้** ไม่ใช่วันที่

วันที่หมดอายุ**ตามปฏิทิน** ส่วน dependency หมดอายุ**ตามการเปลี่ยนแปลง** — สองอย่างนี้ไม่ตรงกัน
⇒ ทุก claim ที่ผูกกับสภาพเครื่อง ให้แนบ **คำสั่งที่สถาปนามันขึ้นมาใหม่ได้** ไม่ใช่แค่วันที่

```yaml
claim:    thclaws engines ใช้งานได้
measured: 2026-08-04 00:05        # บอกว่า "จริงตอนไหน"
valid-if: bash verify-check.sh binexists thclaws   # บอกว่า "ยังจริงอยู่ไหม"
```

- `measured` **ไม่ใช่การรับประกัน** มันคือ timestamp ของการวัดครั้งหนึ่ง
- `valid-if` ต้องเป็นคำสั่ง**บรรทัดเดียว รันเร็ว ไม่มีผลข้างเคียง** — ถ้ามันแพง คนจะข้าม
- ถ้าเขียน `valid-if` ไม่ได้ **แปลว่ายังไม่รู้จริงว่า claim นั้นขึ้นกับอะไร** — นั่นคือคำตอบในตัวมันเอง

**ทำไมมันถึงเป็นกลไกจริง**: ajfon เสียแค่ **หนึ่งคำสั่ง** ในการพบว่าข้อของผมตกยุค เพราะเอกสารแนบ
เครื่องมือที่ทำให้การวัดซ้ำถูก — *"it cost me one command because you shipped the tool that made
re-measuring cheap"* ⇒ **ราคาของการวัดซ้ำ คือสิ่งที่ตัดสินว่ากฎนี้จะถูกใช้จริงหรือถูกอ่านผ่าน**
