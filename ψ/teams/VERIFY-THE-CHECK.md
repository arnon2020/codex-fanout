## กติกา 4 ข้อ ก่อนพิมพ์คำว่า "ตรวจแล้ว"

**1. ตัวตรวจแมตช์ตัวเองได้ไหม**
สตริงเป้าหมายอยู่ใน command line ของคำสั่งตรวจ ⇒ มันจะนับ/เจอตัวเองเสมอ

**2. ทิ้ง output ไปหรือเปล่า**
คำถาม "ของขึ้นไหม" ตอบด้วย output ไม่ใช่ด้วย exit code เพียงอย่างเดียว

**3. query ครบขอบเขตไหม**
sweep/glob/grep ที่ไม่ครบ ให้ผล "ไม่เจอ" ที่**ไม่ใช่** "ไม่มี" — ต้องประกาศ coverage ก่อน

**4. ตรวจถูกชั้นไหม — และตรวจที่ "ปลายทางของ claim" หรือที่ "ปลายทางที่เราคุม"**
string ตรง ≠ ไฟล์มี · ไฟล์มี ≠ รันได้ · รันได้ ≠ ทำงานถูก · จอบอก ≠ ปลายทางได้รับ

🔑 **wrong-endpoint error — รูปเดียวกันคนละชั้น** `[2026-08-04]`
| ใคร | วัดที่ไหน | ควรวัดที่ไหน |
|---|---|---|
| ผม | **inbox ของตัวเอง** (มีคำตอบกลับมาไหม) | **transcript ของ lucifer** (เขาลงมือหรือเปล่า) |
| atlas | **exit code** ของ check | **บรรทัด output** ที่บอกว่าไป fallback path |
⇒ **วัดที่ปลายทางที่ claim พูดถึง ไม่ใช่ปลายทางที่เราเข้าถึงง่าย** · ทั้งสองเคสให้ "ผ่าน" ที่ผิด

## ตารางแปลง: เขียนแบบไหนแทนแบบไหน (ทุกแถวมาจากความพลาดจริงวันนี้)

|---|---|---|---|
| binary มีจริงไหม | `command -v x` อย่างเดียว | `verify-check.sh binexists x` = `[ -x "$(command -v x)" ]` | ⚠️ **แก้เหตุผล 2026-08-04**: dangling symlink ธรรมดา `command -v`/`type -P`/`which` **จับได้หมด** (atlas ทดสอบ ผมทำซ้ำยืนยัน) · เคสที่มันโกหกจริงคือ **bash hash cache** — รันแล้วลบไฟล์ ยังคืน rc=0 พร้อม path เดิม · **ส่วนเคส thclaws ของผมคือ "ไม่ได้ตรวจเลย" ไม่ใช่ข้อบกพร่องของ `command -v`** |
| มีโปรเซสรันอยู่กี่ตัว | `pgrep -f "x --flag"` | `verify-check.sh procs x` (อ่าน `/proc/*/exe`) | `pgrep -c` ตอบ **2 ทั้งที่เหลือ 0** — มันนับคำสั่งตรวจของผมเอง |
| engine boot ไหม | `cmd >/dev/null 2>&1` แล้วดู exit | `verify-check.sh bootprobe '<cmd>' 8` | ทิ้ง stderr → สรุปว่า 3 engine พัง ทั้งที่มัน boot + โหลด 55 skills |

| ไฟล์นี้ dirty ไหม | `git describe --dirty` | `git status --porcelain -uno` + `git describe --tags --dirty` | atlas ลืม `--tags` → ได้ `v0.4.1-228` เกือบรายงานว่าเลขไม่ตรงกับของผม |
| หา key/ค่าใน config ครบไหม | glob เดาเอา (`maw.config.50.json*`) | `ls` ทุกไฟล์ก่อน แล้วประกาศว่า sweep อะไรบ้าง | ajfon ตกไป 2 ไฟล์ → สรุปผิดว่า "วางคีย์ที่เวลานั้นไม่ได้" |

### กลไก ไม่ใช่คติ: `valid-if` — spec v2 (หลังถูกทดสอบและแก้โดย atlas + ajfon)

วันที่หมดอายุ**ตามปฏิทิน** ส่วน dependency หมดอายุ**ตามการเปลี่ยนแปลง** — สองอย่างนี้ไม่ตรงกัน

```yaml
claim:        <ข้อความ>
class:        machine-state | historical | verdict | prediction   # A2 — บังคับ
measured:     <บันทึกของการรันจริง ไม่ใช่วันที่ที่พิมพ์เอง>          # A3
valid-if:     <คำสั่งบรรทัดเดียว เร็ว ไม่มีผลข้างเคียง>            # เฉพาะ class: machine-state
falsified-at: <ครั้งที่ "เห็นมันคืนค่าไม่ใช่ 0" จริง ๆ>              # A1 — ประตูรับเข้า
env-binding:  <check นี้จริงในสภาพแวดล้อมไหน>                      # atlas recursion
```

**A1 (ajfon) — ไม่มี `falsified-at` = ยังไม่รับ** 🔴 **[พิสูจน์เชิงประจักษ์โดย atlas · แก้เป็น A1.1/A1.2 หลัง lucifer จับ]**

> ⚠️ **ajfon แก้กฎของตัวเอง (D10, 2026-08-04)**: *"A1 อย่างที่ผมเขียน **อ่อนเกินไป และจะรับ
> sham fixture ของ lucifer เองด้วยซ้ำ**"*

**A1.1 — ต้องเห็นล้ม *ภายใต้สภาพผิดจริง*** (เครดิต lucifer · ajfon เรียกว่าเป็นครึ่งที่คมกว่า)
ป้อน string ปลอมให้ `grep` = พิสูจน์ว่า **predicate แยกแยะได้** · ไม่ใช่ว่า **pipeline ล้มได้**
**คนละ claim และ A1 มีไว้เพื่ออันหลัง** ⇒ สภาพผิดจริงเช่น: **ถอดเครื่องมือออกจาก PATH ·
สลับ symlink บนสำเนา · วางยา hash cache** (สามอย่างที่ lucifer กลับไปทำเอง)

**A1.2 — check ที่เห็นแต่ "ล้ม" ก็เป็นเครื่องผลิต false-negative พอ ๆ กับที่เห็นแต่ "ผ่าน" ผลิต false-green**
